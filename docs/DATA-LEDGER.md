## 4. `--since` 的真实语义（预测候选条数时必须按这条算）

`--since` 走 `Date.parse(options.since)`（`wechat-snapshot.ts:126`），`"2026-09-10"` 被解析成
**UTC 午夜 = 上海 08:00**，然后与带 `+08:00` 的 `sentAt` 比较。所以 `--since 2026-09-10`
的含义是「2026-09-10 **08:00**（上海）之后」，不是当天零点。

实测后果（用真实代码路径取，不是按日期算）：

- 温州爸妈 09-10 当天有 10 条，`--since 2026-09-10` 只拿到 **6 条**（4 条在 08:00 前）。
- 亲爱的爸爸妈妈 09-09 当天有 2 条，`--since 2026-09-09` 拿到 **0 条**（两条都在 08:00 前）。
  上一版按日期推断这里有 2 条，**错了，已订正**。

**精确限制到 N 条的能力：现在没有。** 驱动脚本只有 `--only`（选会话）和 `--since`（到天，且带上面
那个 08:00 偏移），没有条数上限。底层 `loadWechatBundle` **已经支持** `maxMessages`，对 since 过滤后
的列表按文档顺序 `slice(0, maxMessages)`（`:146`、`:164`），但驱动把它硬写成
`Math.max(messages, 1)`（`wechat-import-all.mjs:165`），等于不截断。

**最小实现方案**：在 `wechat-import-all.mjs` 加一个 `--max-messages`，透传给 `runWechatImportWorker`
的 `maxMessages`，并在 dry-run 日志里打印"将导入 N 条（该窗口共 M 条）"。不改解析器、不改
`canonicalMessageId`、不改去重逻辑、不改 schema。**本轮不改代码。** 在它落地之前，
只能用"`--since` 恰好等于 6 条"的窗口，不能靠 `--since` 扩成几十上百条再指望别处收窄。

### 口径订正：那 52 张无日期 HEIC 不能算"已证明不在库"

上一版把它们并进"已证明未命中"，**这一步推得太远，现已撤回**。理由是 HEIC 的入库身份不是原件的
sha：有日期的 HEIC 走的是"先转码、再按**转码产物**的 sha 入库"这条路，所以库里存的 checksum 是产物的，
不是原件的。**拿原件 sha 去查 `media_assets.checksum` 得到 0 命中，只说明"没有以原件 sha 为身份的行"，
不能证明"不存在对应的转码资产"。**

这 52 张在 `quark-heic-converted-task-items.jsonl` 里**没有 crosswalk 条目**，所以两个方向都没有证据：
既没有产物 sha 可查，也没有映射可追溯。按"证据不足允许保留无法确认"的规矩，它们的状态是
**关联无法确认 + 当前不可执行**，两条都成立，不再往"缺失"或"已存在"任何一边靠。
**本轮不继续扩查**（会需要对 52 个原件逐个做一次可复现的转码并按产物 sha 反查，属于转码动作，不在授权内）。

### 一、方法：按会话标签比对，不按全库比对

上一版把每条消息的文本摘要拿去**全库**比，结果私聊里几乎每句短话都"见过"，把 2,799 条判成无法确认，
没有信息量。本清单改成**先认会话、再判存在**：

1. 先用「文本摘要多重集重合」+「共享媒体 checksum」认出每个导出文档对应库里哪个（些）标签；
2. 只在**它自己的**标签范围内判断一条消息是否已存在。别的会话里出现同一句话，那是别人的消息，
   不是这条消息的证据。
3. **出现次数全程保留**：摘要 d 在文档里出现 m 次、在自己标签下出现 n 次，则 `min(m,n)` 条算已存在，
   余下 `m-n` 条算缺失。不折叠、不去重。
4. **纯媒体消息**不靠文本（它的文本就是 `[media]`，全库到处都有），靠**媒体 checksum 是否挂在自己
   标签的行上**判断。没有可用 checksum 的（引用解析不了或文件不是 JPEG）一律进"无法确认"。

| 温州爸妈 | 876 | 6 | **安全**：这 6 条就是本轮已入库的同六条，`canonicalMessageId` 完全相同，会被判 `reused`，不会重复写 |

**最小修正方案（本轮未实现，需单独授权）**：给导入链路加一个**消息 id 白名单**。

1. `WechatBundleOptions` 增一个可选 `messageIds?: ReadonlySet<string>`；
   `loadWechatBundle` 在现有 `since` 过滤之后、`slice(0, maxMessages)` 之前再过一道
   `filter(m => messageIds.has(m.messageId))`。**顺序很重要**：先时间、再白名单、最后截断，
   否则截断会先吃掉名单内的消息。两处过滤点（`:144` 与 `:163`）都要改，它们必须保持一致。
2. `scripts/wechat-import-all.mjs` 增 `--id-file <path>`，读一个每行一个 `canonicalMessageId` 的

3. dry-run 必须打印"名单 N 条、匹配 M 条"，**M≠N 就停**。
4. 不改解析器、不改 `canonicalMessageId`、不改去重逻辑、不改 schema。

## 13. 订正后的正式清单（取代第 12 节的数字）

### 一、判定键换成「时间 + 发送人 + 内容」的组合键

共享媒体 checksum 是有力支持，但**单独不能证明旧标签归属**——同一张照片可以被转发到别的会话。
所以改用组合键：**UTC 瞬间 + senderDigest + sha256(入库文本)**，出现次数全程保留
（某键在文档里出现 m 次、在自己标签下 n 次，则 `min(m,n)` 已存在、余下缺失）。

这一换，把第 12 节两处问题一起解掉了：

- **「无法确认」这一类整个消失**。之前纯媒体消息只能靠 checksum 判，判不了就进无法确认；
  组合键里有瞬间和发送人，纯媒体消息同样可判。现在每条消息都有结论。
- **乳儿班那 3 条"已存在"、爸爸妈妈那个不可信的 3/4 拆分，都是文本巧合**。组合键下，
  这两个会话与库里**没有一条**组合键相同。爸爸妈妈因此不再需要人工确认，它是 7 条全缺。

### 五、452 个引用、415 份内容、411 个新资产的对应关系

**不能写成"新增 411，其中复用 19"**——复用的不是新增的一部分，两者是同一层的并列项：

```
452 个可持久化媒体引用（每条带媒体的消息正好 1 个）
  ↓ 按内容 SHA-256 归并
415 份不同内容                     ← 452 − 415 = 37 个引用指向批内已被别的消息引用过的同一份内容
  ↓ 与全库 media_assets.checksum 比
411 份是档案里没有的  →  新增 411 行 media_assets
  4 份已经在档案里    →  复用，新增 0 行 media_assets
```

「批内重复 37」是指**同一批里不同消息引用了同一份内容**（转发、同图重发）。它们各自仍然产生一条
`media` 行和一条 `wechat/original` 位置行，但共用一个资产。

### 八、`--id-file` 已实现（本轮代码改动）

`scripts/wechat-import-all.mjs` 新增 `--id-file <path>`，指向一个 JSON：
`{ document, fileSha256, conversationId?, messageIds: [...] }`。

- **过滤顺序是 `since` → 白名单 → 截断**，写进 `loadWechatBundle`（`WechatBundleOptions.messageIds`）。
  顺序是要点：白名单在 `since` 之前会把按时间排除的消息捞回来；截断在白名单之前会悄悄少导。
- **名单内容哈希并入完成键**：`${digest}|${since}|ids:${sha256(排序后的 id 列表)}`，
  两个不同批次不会互相标记完成。
- **以下情况一律显式失败退出，绝不少导**：JSON 读不了；`messageIds` 空或非字符串数组；
  **名单内有重复 id**；`fileSha256` 不是 64 位小写十六进制；**来源文件 SHA 与批准值不符**；
  `conversationId` 不符；**名单匹配数 ≠ 名单条数**（报"matched M of N"）；

# 旅行模块：设计与实施计划

> 性质：新模块的设计稿与分期计划，长期维护（改这里，不另开带日期的副本）。
> 提出：Teddy，2026-09-24。「记录我们和张年去过的地方，大大小小的旅行。」
> 导航：首页 · 记忆 · 健康 · **旅行** · 妈妈月报。
> 前提：读完 [`nianlife-product-principles.md`](nianlife-product-principles.md)；本文每一节都对着它的八条检验句写。

---

## 0. 定位：旅行是记忆的地理章节，不是第二份记忆

「记忆」按时间翻，一天一天。旅行页按**地方**翻：张年到过哪里、每一次离开杭州是怎么回事、下一次要去哪。
它和记忆的关系是**索引与正文**——旅程页不重写日子，每一天都指回已经发布的日页
（`/memory/YYYY/MM/DD`），来源链继续由日页承担（原则八）。旅行页新增的只有三样东西：

1. **地点结构**（去过的国家 / 省 / 城市 / 地方，以及坐标），这是现在整个站里没有的；
2. **旅程聚合**（把 2025-12-26 到 12-31 这六天合成「四川跨年」这一件事）；
3. **规划**（接下来去哪，家里聊过的、系统建议的、爸妈自己填的）。

一句测试（原则 §6）：一个 30 岁的张年打开它，能看到自己 11 个月大时被抱着站在雪山湖边，
第一次坐火车是去合肥，出生后的第一程飞行是从美国回杭州——**是**。

### 1.3 照片 GPS 怎么用起来

- iPhone 原片的 GPS 在夸克那条线上是保留的（上面的 71%）。微信那条线要看是不是「原图」：微信压缩过的图会剥掉 EXIF（本机微信导出图的实测结果见 §1.4）。
- 补一步导入：用 `exifr` 读 `GPSLatitude / GPSLongitude / DateTimeOriginal`（HEIC 也能读；必须在 heic-convert 之前读，转换会丢 EXIF），
  存到新表 `media_geo`（`media_asset_id, lat, lng, taken_at_exif, source`），不改 `media_assets`。本机已下载的 2,023 张可以直接回填，不用重新下载；
  R2 里的原件字节完整，以后也能补。
- 有了坐标，旅程提取的 A 步多一条硬证据：某天有 ≥3 张照片落在杭州市域外 → 自动成候选窗口；地图上的城市点直接由坐标聚出来，
  不再全靠正文里的地名。坐标 → 城市用本地的省市边界（同一份 GeoJSON 做点在多边形内判断），不调外部地理编码。

### 1.4 微信图片实测：没有 GPS

本机 WeFlow 导出（`E:/WechatHis/texts`，19,254 张 jpg）抽 1,500 张读 EXIF：**0 张带 GPS**。微信发图时把 EXIF 剥掉了，
这条线上的照片永远只能靠聊天时间和正文定位。所以坐标只来自夸克那条线（iPhone 相册原片），微信照片要定位，
只能借同一天夸克原片的坐标或正文里的地名——这也是为什么正文提取那一步不能省。

即：**2 个国家（中国、美国）**，约 **10 个城市**，十几次出行。「熊猫」「飞机」这类词大量误报
（玩具熊猫、练习坐飞机），所以关键词只能划候选，不能定结论——和 CLAUDE.md 的分工一致：
本地程序缩范围，模型判语义，人确认。

## 2. 概念模型

三个对象，都是小 JSON，人能读、能手改、能整体带走（原则八）。

### Place · 地点

```
{ id: "cn-sc-chengdu", name: "成都", level: "city",        // country | province | city | spot
  parent: "cn-sc", country: "CN", adcode: "510100",
  lat: 30.57, lng: 104.07 }
```

几十条，**手工维护的小地名册**（`places.json`），不接外部地理编码。省用 adcode 对上地图 GeoJSON。

### Trip · 旅程

```
{ id: "2025-12-sichuan", title: "四川跨年", kind: "travel",   // travel | hometown | birthplace | daytrip
  fromDay: "2025-12-26", toDay: "2026-01-01",
  placeIds: ["cn-sc-chengdu", "cn-sc-panda-base", "cn-sc-lake"],
  stayPlaceId: "cn-sc-chengdu",
  days: ["2025-12-26", "2025-12-27", ...],          // 指回日页，不复制正文
  coverMediaId: "...", summary: "一段话，讲这次旅程整体是怎么回事",
  firsts: [{ text: "第一次看见雪山", day: "2025-12-28" }],
  transport: ["flight"], companions: ["爸爸","妈妈","雪姨"],
  status: "confirmed",                                 // draft | confirmed
  evidence: [{ day: "2025-12-26", quote: "就带那个大箱子" }] }
```

规则：离开杭州市域、至少整日在外 → 一个旅程；连续在外的日子合成一个；回老家算 `hometown`；
一日往返算 `daytrip`。**没有日页的日子不能成为旅程的一天**（旅程只是索引）。

### Plan · 规划

```
{ id: "...", title: "国庆去大湾区", placeIds: ["cn-gd"],
  when: { kind: "window", from: "2026-10-01", to: "2026-10-07" } | { kind: "unconfirmed", text: "国庆" },
  status: "wish" | "tentative" | "fixed" | "done" | "dropped",
  origin: "family_chat" | "suggested" | "parent",
  upcomingItemIds: ["..."],  note: "...", suggestedReason: "...",
  editedBy: "mom" | "dad", editedAt: "..." , tripId?: "..." }
```

`done` 的规划要指向一个真实旅程（`tripId`），否则只能是 `fixed`——和待办的「删除线要证据」是同一条规矩。

## 3. 数据放哪、怎么到线上

沿用月度正文的方式：**仓库外的文件目录，脚本写、页面读、scp 发布**，不进 `life_events`，不给页面新增大表读取
（`getStore()` 那条禁令继续有效）。

| 内容 | 路径 | 读写 | 谁写 |
|---|---|---|---|
| `places.json` `trips.json` | `/srv/nianlife-content/travel/` | 页面只读 | 本地脚本经 scp 发布（同 `nightly-editor.mjs` 的路子） |
| `plans.json` + 变更历史 | `/srv/nianlife-travel/record/` | 页面可写 | `/travel/plans` 里爸妈编辑；夜间脚本合并待办与建议 |

- 前两者落在已有的 `CONTENT_MOUNT`（`/srv/nianlife-content` 只读挂载）里，**第一、二期不用改部署脚本**。
- 规划的可写目录第三期才需要，那时给 `deploy-ecs-public.sh` 加 `TRAVEL_MOUNTS`，照 `HEALTH_MOUNTS` 的样子。
- 环境变量：`TRAVEL_CONTENT_DIR`（缺 = 页面说「还没有整理出旅行」）、`TRAVEL_RECORD_ROOT`（缺 = 规划只读）。
- 读取层 `lib/travel/` 带 300 s 内存缓存，和 `loadMonthContent` 一样；旅程页里的照片走现有的
  `resolveMonthContentMedia` + deliverability 门，不另起一套。

## 4. 页面

路由：`/travel`（总览 + 地图 + 旅程列表 + 接下来）、`/travel/[tripId]`（一次旅程）、`/travel/plans`（规划与编辑）。
导航加第五项「旅行」，位置在健康和妈妈月报之间（Teddy 给的顺序）。手机底栏从 4 列改 5 列——字号 `.8rem`
四个字宽的「妈妈月报」在 5 列里要实测，必要时底栏用 `13px`。

### 4.1 `/travel` 总览

自上而下：

1. **一句话**（原则一：不点任何东西就能读出）。例：「张年 1 岁 8 个月，去过 2 个国家、10 个城市。最近一次是 8 月中的宁波。」
   数字在这里是允许的——这一页的主题就是「去过哪」，但只此一句，下面全是内容。
2. **迷雾地图**（§5）。
3. **旅程**：按时间倒序。多日旅行是大卡（封面 + 标题 + 日期与当时几岁 + 一句综述）；一日短途是窄条
   （原则五：一眼分得出四川跨年和去德清看羊）。回老家用一个小标「回温州」「回西安」，不与出游混。
4. **接下来**：最多 3 条已定或初定的规划，一句话一条，链到 `/travel/plans`。没有就整块消失，不写「暂无」。

### 4.2 `/travel/[tripId]` 旅程页

封面照 → 标题 → 「2025 年 12 月 26 日 – 2026 年 1 月 1 日 · 当时 11 个月」（两个时钟） → 去了哪（地点链，点省份回地图）
→ 一段综述 → 「这次的第一次」（有才出现） → 逐日：日标题 + 首段 + 那天的照片（复用 `DayPhotos`），整段可点进日页
→ 折叠的「当时留下的资料」直接复用日页的来源块。旅程页**不写新故事**，综述是唯一新文字，要有 `evidence`。

### 4.3 `/travel/plans` 规划

三栏状态：想去 / 初定 / 已定；每条显示谁提的（家里聊到的、系统建议的、妈妈填的）、大概什么时候、一句备注。
编辑：新增 / 改状态 / 改日期 / 备注 / 不要了。写入沿用健康记录那套（同源检查 + 「谁填的」只是声明，
不是身份），存 `TRAVEL_RECORD_ROOT`，每次改动留历史。**没有登录**（当前优先级明确不做）。

系统建议区：最多 3 条，各带一句理由（「去年 12 月在四川看过熊猫，这个冬天可以去看雪」这种，不是「推荐指数 9.2」），
爸妈可「收下」（变成想去）或「不要」（记住，不再推）。

## 5. 迷雾地图

- **不用地图 SDK、不用外部瓦片**。国内真机是标准，站是私站，三个读者；一张服务端渲染的内联 SVG 足够。
- 底图数据：中国省级 GeoJSON（阿里 DataV GeoAtlas `100000_full`，标准地图数据，含港澳台与南海诸岛，不裁剪），
  在本机简化到 ≈300 KB 存 `v2/public/geo/china-provinces.json`；投影自己写（等距圆柱或简单的 Albers），
  或引 `d3-geo`（≈30 KB），二选一，实施时定。
- **世界层**：只在有国外地点时才出现——现在就有（美国）。用 Natural Earth 110m 国家轮廓（≈200 KB），
  放在中国图下面，小一号，标题「走出过国门」。
- 视觉（对照原则 §4）：暖纸底；未到过的省份是淡雾（纸色略深 + 极细的纸纹），到过的省份填鼠尾草或陶土面色，
  城市是陶土圆点 + 名字；点一个省，下面列出在那里的旅程与「当时几岁」。不做缩放、平移、街道级。
- 手机上是一张静态图 + 图下的列表；桌面上可以 hover。
- 「解锁」的定义 = 有一次 `confirmed` 旅程的 `placeIds` 落在那个省 / 国家。地图只读 `trips.json` + `places.json`，不查库。

## 6. 旅程提取管线

分工照 CLAUDE.md：本地程序缩范围 → 模型判语义 → Claude 编排与抽检 → 人确认 → 发布。

| 步 | 做什么 | 谁 |
|---|---|---|
| A 候选窗口 | 扫月度正文（标题、正文、来源消息）：地名、交通词、「出发 / 回杭 / 到家」；连续命中的日子并成窗口 | 本地脚本 `scripts/editor/travel-candidates.mjs` |
| B 判定 | 对每个窗口回答：有没有离开杭州、去处（省 / 市 / 地方）、性质、起止日、途中的「第一次」、一段综述；每个结论附原句和日期 | 项目现用的编辑模型路径（`day-writer` 走的那条无头写手；照片画面继续用 DeepSeek 已有描述，不重新识图） |
| C 校验 | 综述里的引语逐字对得上来源、称谓走注册表、没有「有人 / 大人」——**直接复用 `validate-day.mjs`** | 本地 |
| D 确认 | 写 `.data/travel-candidates-<日期>.md` 给 Teddy 勾；清楚的（正文已明说去处和起止）Claude 抽检后标 confirmed，模糊的留 draft 不上页 | Claude + Teddy |
| E 发布 | 合成 `trips.json`，scp 到 `/srv/nianlife-content/travel/`，留 ledger | 本地脚本 |
| F 夜间增量 | `nightly-editor.cmd` 加一步：只看昨晚新写的日子，落进已有旅程或开新的 draft | 计划任务 |

地名 → 坐标：`places.json` 手工维护；模型只允许给出地名册里有的 id，给不出就留 `unknown-place` 让人补。

## 7. 规划与推荐

三个来源，一张表：

1. **家里聊过的**：`upcoming_items` 里 category=出游、review approved 的行 → 夜间脚本写成 `origin: family_chat` 的规划，
   带 `upcomingItemIds`，日期与状态照搬（tentative → 初定；有 window 的保留）。首页待办里它们照旧显示——那是待办视角，旅行页是去处视角，不算重复。
2. **爸妈填的**：`/travel/plans` 编辑。
3. **系统建议**：每月一次（夜间任务里的一步），给模型的材料是：当时年龄、季节、已解锁地点、家里聊到过但没成行的地方（待办里的莫干山、四明山、舟山、大湾区）、
   上一次出行距今多久；要它给 3 条，每条一句理由、一个大概时间窗、一个 `placeId`。**不出现「推荐指数」「AI 为你」**——建议就像家里谁随口提了一句。
   已被「不要」过的地方不再提。

规划变成现实：某次旅程 confirmed 后，脚本按地点和日期匹配 `tentative / fixed` 规划，提示合并（不自动改成 done）。

## 8. 八条原则逐条对照

| 原则 | 这个模块怎么过 |
|---|---|
| 一 Person First | 总览第一句是张年去过哪，不是「地图 / 列表 / 规划」三个功能入口 |
| 二 Two Clocks | 旅程、逐日、规划都显示「日期 · 当时几岁」；地图点省份也显示当时几岁 |
| 三 Media First | 页面不出现 trips.json、candidate、upcoming、model 这些词；「11 张照片」这类计数不出现，只有总览那一句「几个国家几个城市」 |
| 四 Invisible Automation | 旅程由夜间增量自己长；规划编辑是可选的，不是主按钮；没有空状态引导上传 |
| 五 Not Equal Weight | 多日旅行大卡、一日短途窄条、回老家小标；draft 不出现 |
| 六 Bring the Past Back | 规划页的「建议」引用真实旧旅程（「去年这时候在西安」）；地图本身就是过去在回头看人 |
| 七 Automatic Reflection | 旅程综述去掉数字仍是一段能读的旅行记 |
| 八 Family Owns It | 三个 JSON 人可读；每次旅程指回日页，日页指回来源；综述带 evidence；规划每次改动留历史 |

## 9. 分期与验收

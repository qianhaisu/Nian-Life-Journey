## 两个残留缺陷（同属来源绑定，P1）

### 1. 后来新增的来源被回填进旧事实版本

合成复现：o1 v1 只有 s1；导入 o1 v2 时新增 s2 支持链。`traceObservation(o1).observation.versions[0].sources` 却列出 s2，并带 later-evidence 正文，boundVersion 为 null。

根因：`timeline.ts` 的 sourceRefs 对所有当前有效来源链接都生成历史视图；`bindingAt(link, oldVersion)` 为 null 时回退当前来源版本。null 在此代表“该旧事实版本尚未具有此绑定”，不是“可以取最新版本”。因此即使绑定数组追加保存，旧版本展示仍被未来来源污染。

最小修复：历史版本仅展示当时已存在且适用的来源关系；没有绑定不可回退当前证据。后来撤销/更正关系也应区分当前视图与历史版本审计，不用当前过滤器抹去历史依据。覆盖新增支持源、不同事实版本、后续来源再更新；旧版本追溯内容保持不变。保留原件和追加审计，不重写既有绑定。

### 2. 待复核绑定不持久，明确确认被当作重复忽略

合成复现：先有 o1 v1→s1 v1；单独导入 s1 v2；再导入 o1 v2 未说明来源版本，首次 plan 返回 needsReview=true 并沿用旧绑定。原样重放同一输入却 needsReview=false。随后为**相同 o1 v2 正文**补交 toVersion=2，链接仍返回 duplicate，实际绑定保持 v1。

根因：unconfirmed 只在本次 fromVer>fromNow 时计算，没有持久待决状态；显式确认也被同一新事实版本条件拦住。用户必须改正文才能让绑定更新，违背只确认依据、不编造新事实的工作流。

最小修复：待决状态持久记录并在重复导入、查询和时间轴中保持可见；提供现有导入/审核通路可完成的明确确认，不要求为触发版本而修改正文。确认要留操作者/依据及前后绑定的审计记录，重复确认幂等；冲突确认不静默覆盖；历史版本仍保留原始绑定。不能仅把同一 from 版本的末尾值覆盖旧绑定视为历史保存。

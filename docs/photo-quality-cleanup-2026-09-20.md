# 照片画质清理（2026-09-20）

Teddy 2026-09-20 指出 `https://nianlife.cn/memory/2025/07/24` 查看器里第 3 张照片糊得没法看，
要求把这一类照片统一从展示里去掉。本文是这次只读排查与处置的脱敏记录；逐张清单、联系表和
样本标识留在仓库外的私有目录，不进 Git。

## 一、糊的原因：原生分辨率不足，不是拍糊，也不是管线出错

样本那张在三层记录里是同一个尺寸：展示层 `media` 行、`media_assets` 源尺寸、以及实际投递给
查看器的 `web` 派生图，全是 **90×120**。查看器把它按屏幕宽度铺开，等于放大十几倍。

排除了另外两种可能，都是全库量过的，不是抽样推断：

- **不是派生图被放大**：可投递的照片里，派生图短边大于源图短边的有 **0 例**。
- **不是派生图被做小**：源图短边 ≥720 却只生成出 <480 的 web 派生图的有 **0 例**。
- **不是查看器请求错了变体**：`components/photo-viewer.tsx` 用的是 `photo.src`（web 变体），
  缩略图条另走 `thumbnailSrc`，两条路都指向同一个资产，`app/api/media/[id]` 也没有变体错配。

也确认了**救不回来**：这些小图所在资产下的每一条 `media_locations`——包括 `provider='wechat'`
的 `original`——尺寸同样小，库里没有更高质量的授权原图可以替换。源尺寸的取值是微信缩略图的固定
规格（`157×210`、`67×120`、`90×120`、`135×180`、`210×157`…，还有 19 张 `20×20` 的界面图标）。

> 措辞上的区别很重要：这 1,312 张**不是「画面拍糊了」**，是**原生分辨率不足**。前者是这一张拍
> 坏了，后者是当年微信只留下了缩略图。

## 二、为什么不按清晰度分数切

把线上展示中短边 ≥240 的 **4,173 张**全部归一化到同一短边后重算 `sharp.stats()`（跨尺寸可比），
分数最低的 100 张做成联系表逐张看过：几乎全是新生儿睡觉的特写、白被子、素墙——**低纹理场景，
不是拍糊**，而且正是最不该撤的那批照片。分数分布也是连续的（p1=0.61、p5=1.00、p50=2.47），
切在哪都是人为划线。

反向同样成立：仓库里既有的 `v2/data/photo-quality.json` 是在**各自原尺寸**上算的，跨尺寸不可比
——同一天里 240×237 的小图算出 2.23，比 1080×1254 的清楚大图（1.68）还「高」。那份缓存保留，
但不作跨尺寸排序用。

**结论：不按清晰度撤任何照片。**

## 三、判定标准：三层尺寸证据里最大的短边 < 160

门槛不是新造的数，是项目自己的既有标准。`v2/lib/media/hero.ts` 里的 `THUMBNAIL_MIN_SIDE = 160`
写着「能填满一个网格格子而不明显放大的最小尺寸」，首页（`lib/home-memory.ts` 的 `usable()`）
早就在用它挑照片——所以首页从来没有出现过这类小图。漏掉这条线的是日页、月页、月相册和来源材料：
它们只过可投递性和主体 `store_only`，不过尺寸。

线上展示照片的短边实际分布也支持这条线：

| 短边 | 张数 |
| --- | --- |
| <160 | 1,312 |
| 160–239 | 11 |
| ≥240 | 4,173 |

160–239 这一带只有 11 张，已**逐张**看过，画面都清楚，一张都不撤；240–719 的 5 张同样逐张看过，
全部保留。门槛落在几乎没有样本的真空带里。

判定取**三层证据里最大的那个短边**：展示层 `media` 行、`media_assets` 源尺寸、该资产下每一条派生
图的尺寸。任何一层证明这张图够大就不撤——一行陈旧的缩略图元数据不该决定一张能救的照片的去留。
三处都不可用时判 `unknown`，**留着不动**：缺数据不是撤下的理由。

## 四、怎么撤：一道共用闸门，纯代码，可逆

规则在 `v2/lib/media-quality.ts`，接进 `v2/lib/media/deliverability.ts` 的 `deliverableMediaIds()`。
选这里是因为它是**唯一一道所有阅读面都经过的闸门**：

- `lib/family-archive.ts` → 首页、`/memory` 索引、月页、月相册、日页的照片与计数；
- `lib/day-reading.ts` → 日页的来源材料；
- `app/events/[id]/page.tsx` → 故事详情页。

一道闸门意味着不会出现「首页没有、点进去却有」的不一致，也不用在每个组件里各打一个补丁。

明确不做的事：

- **不写数据库**，一行都不写；
- **不碰主体账本**。`media_subject_check` 说的是「画面里是不是他」，和分辨率是两件事。
  R1 曾提出借那条通道写 `store_only`，总指挥复核否决：那会在主体/隐私账本里留下 1,312 条不是
  在谈主体的行，且分类码（`kind:life` / `subject:uncertain` / `sensitive:none`）没有逐张验证。
  该方案已撤销，脚本已删除，**从未执行过**；
- **不删原件、不删 media 行、不改故事和来源链接、不动任何既有审核决定**；
- 月份的章节仍由家庭可见媒体决定，所以一个月的照片即便全被挡下，**这个月依然在**
  （「withheld is not missing」对画质同样适用）；一个日页的照片全被挡下时，**文字与历史照常在**。

**回滚**：把这两个文件的这段改回去即可。没有账本行要撤，没有数据要还原；回滚后重新出现的应当
恰好是私有清单里那 1,312 张。

## 五、覆盖与数量

只读盘点的范围与结果：

| 项 | 数 |
| --- | --- |
| 库中可投递的照片（非 private、有 ready 的 hot/oss 派生图） | 11,227 |
| 按家人真实浏览路径爬取到的线上媒体引用（21 个月 / 475 个日页，抓取失败 0） | 5,717 |
| 其中照片 | 5,496 |
| 其中视频（本规则不管） | 221 |
| 归一化清晰度复扫（短边 ≥240），成功 / 失败 | 4,173 / 0 |
| **闸门会挡下** | **1,312** |
| ├ 短边 ≤120 | 262 |
| └ 短边 121–159 | 1,050 |
| 判 `unknown` 而保留的 | 0 |
| 已被主体审核撤下、与本次无关的 | 0 |

出现位置：1,312 张全部只出现在月页与日页，**首页一张都没有**——首页既有的 160 下限早就把它们挡
在外面了，这也反过来印证门槛选得对。

代价（家人会少看见什么）：

- 受影响最重的是 2026-03（517 → 228）、2026-06（380 → 155）、2026-04（453 → 287）——这几个月
  日常记录里托班转发的 `157×210` 占比高；
- 402 个有照片的日页里，**25 个**会一张照片都不剩（其中 23 个是只有 `≤120` 那档的老日子），
  **160 个**照片变少。这些日页的文字、来源和历史不受影响，地址也还在。

## 六、未验证的部分

- **线上表现未验证**。本轮不部署、不写库，所有结论来自只读盘点、本地规则测试和真实生产数据形状
  的 dry-run。闸门在 nianlife.cn 上的实际效果要等发布后才能确认。
- 「同一张照片是否在夸克那边另有一份全分辨率副本」**没有查**。库里按资产查过，没有更大的
  location；跨资产的同画面副本要靠感知哈希比对，不在本轮范围内。这是唯一已知可能挽回部分照片的
  方向。
- `withheldMediaCount` 现在会把这批算进去。该字段在 `lib/memory-chapters.ts` 里计算，**当前没有
  任何页面渲染它**，所以没有家人看得见的数字因此变得对不上；将来要展示它时需要区分「等派生图」
  和「分辨率不足」。
